### What Went Well

- Every story and implementation received validation or review.
- Review findings resulted in code fixes, regression tests, and runtime evidence.
- The regression suite grew from 513 tests after Story 1.0 to 747 after Story 1.7 while remaining green.
- AD-9 snapshot boundaries, AD-12 frame ordering, Physics ownership, and the StateMachine/FrameDataEngine peer model survived implementation scrutiny.
- The epic established a credible foundation for editor tooling, runtime tuning, training features, and replay integrations.

### Challenges

- Cross-module invariants and failure modes were not explicit enough during story preparation.
- Lifecycle, generation, frame-order, and failure-atomicity problems recurred across modules.
- Several critical boundary defects were discovered during review rather than initial implementation.
- Main-project, scaffold, and Godot runtime parity required repeated verification.
- Tracking state drifted after completion evidence existed.

### Key Lessons

1. Validation and review are essential safety nets, but do not replace risk analysis before implementation.
2. Review discoveries should become reusable preparation checks and regression requirements.
3. Known defects must be closed before increasing system complexity.
4. A large architectural rewrite should be triggered by observable degradation, not concern alone.
5. Automated tests, Godot verification, stakeholder acceptance, and tracking consistency jointly define completion.

### Architecture Escalation Triggers

Trigger architecture review if the same core invariant fails across stories, lifecycle fixes break other modules, EventBus or ownership rules accumulate exceptions, end-to-end behavior cannot be proven, new capabilities must bypass established interfaces, or debt blocks multiple stories.

## 2. Next Epic Preparation

### V2 Epic 2 Preview

V2 Epic 2, Move Authoring & Training Suite, contains EditorPlugin move authoring, runtime tuning and JSON writeback, combo display, input recording/playback, and training state save/load. It depends directly on Epic 1's DataStore, snapshot semantics, state stack, collision events, hot reload, and scaffold behavior.

### Critical Preparation Gates

All gates must close before V2 Epic 2 starts:

1. Bind knockback completion to the exact Hitstun occupancy generation.
2. Reject invalid player IDs before StateMachine knockback-completion handling.
3. Reject rooted and parent-traversing scaffold source-manifest entries.
4. Remove fixed-delay dependence from FileWatcher tests. [PREP-2.2 evidence](evidence/v2-prep-2-2/index.md)
5. Isolate EventBus singleton state between tests. [PREP-2.2 evidence](evidence/v2-prep-2-2/index.md)
6. Establish an immutable boundary for state event payloads.
7. Define the `MoveFrameChanged` / `MoveStarted` ordering contract.
8. Decide and enforce missing-field semantics for physics data.
9. Align Story 1.3, epic, retrospective, and sprint tracking states.
10. Apply a cross-story risk checklist to all five Epic 2 stories.
11. Define required verification evidence per story.
12. Review and update Epic 2 acceptance criteria before kickoff.

### Significant Discovery

Epic 2's product direction remains sound, but its story definitions do not sufficiently express the lifecycle, generation, failure-atomicity, and state-snapshot risks discovered in Epic 1. Epic 2 requires planning review before implementation.

### State Architecture Direction

The current stack-based state machine is adequate for V2 but may not scale to a full fighting game's state complexity. The intended V3 direction is a layered state machine combined with a state stack, tag system, and data-driven event system.

The full redesign is deferred to V3. Epic 2 Story 2.5 must use a versioned state-snapshot contract, capture and restore through dedicated interfaces, avoid serializing mutable arrays or concrete stack containers directly, and define schema migration or fail-fast rejection behavior.
